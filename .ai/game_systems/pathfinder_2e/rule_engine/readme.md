# Submodulo: Pathfinder 2e Rule Engine (Product)

## 1. Proposito
Fornecer os primitivos genericos de regras do PF2e — roll options, predicates e modifiers com stacking — usados pelo restante do sistema para decidir "essa regra se aplica agora?" e "qual e o total de um bonus/penalidade composto por varias fontes?".

Este submodulo e o **substrato** do Rule Engine descrito em `.ai/game_systems/pathfinder_2e/spells/questhub-spell-interaction-effects-plan.md` secao 9, mais as familias de Rule Element ja implementadas sobre esse substrato: `FlatModifier`, `GrantItem`, `RollOption`, `Immunity`, `Weakness`, `Resistance`, `TempHP`, `Sense`, `ActorTraits`, `BaseSpeed`, `Note`, `ActiveEffectLike`, `AdjustDegreeOfSuccess`, `RollTwice`, `TokenLight`, `TokenMark`, `DexterityModifierCap`, `Striking`, `WeaponPotency`, `FastHealing`, `CriticalSpecialization`, `MartialProficiency` e `EphemeralEffect` — 21 familias no total. As que restam (`BattleForm`, `Aura`, `ChoiceSet`, `DamageDice`, `Strike`, `AdjustStrike`, `ItemAlteration`, `DamageAlteration`) exigem contexto de dano/rolagem real ou UI de escolha do jogador que este substrato deliberadamente nao tem, e continuam fora de escopo.

**Primeiro consumidor real conectado**: `.ai/game_systems/pathfinder_2e/character_effects/` guarda efeitos ativos por personagem (`Pathfinder2eActiveEffect[]`, cada um com `rules: Pathfinder2eRuleElementSource[]`) e o calculo de CA (`.ai/game_systems/pathfinder_2e/armor_class/`) resolve os `FlatModifier` desses efeitos via `resolveFlatModifiers` + `applyStackingRules` deste submodulo. E um consumidor deliberadamente minimo (so `FlatModifier` com `selector: 'ac'`) — as demais estatisticas derivadas (saves, Spell DC, pericias, velocidades) continuam sem nenhuma ligacao ao Rule Engine.

## 2. Problema Resolvido
O catalogo de magias/effects (`.ai/game_systems/pathfinder_2e/spells/`) ja importa `Pathfinder2eRuleElementSource[]` losslessly (Fase 1 do plano), incluindo `predicate` e `selector`/`type`/`value` de coisas como `FlatModifier`. Sem este submodulo, esses dados sao apenas JSON opaco — nao ha como avaliar se um predicate bate com o estado atual, nem como somar corretamente varios bonus/penalidades do mesmo tipo (regra de stacking do PF2e, onde bonus do mesmo tipo nao se acumulam).

## 3. Regras de Negocio
* **Roll options** sao um conjunto de strings que descrevem fatos sobre o estado atual (ex.: `self:condition:frightened`, `target:trait:undead`). Este submodulo so define o tipo e funcoes de composicao (`createRollOptions`, `mergeRollOptions`) — quem povoa o conjunto com fatos reais do jogo (personagem, alvo, cena) e responsabilidade de uma fase futura.
* **Predicates** avaliam um array de `PredicateStatement` (formato identico ao usado pelos dados reais do compendio, ja auditado no fechamento de dependencias das magias) contra um conjunto de roll options. Suporta os operadores encontrados nos dados reais: `and`, `or`, `not`, `nand`, `nor`, `xor`, `eq`, `gt`, `gte`, `lt`, `lte`.
* Predicates com expressoes dinamicas Foundry (`{item|level}`, `{item|flags...}` — substituicoes de runtime que dependem de um item/ator concreto) **nao sao resolvidas** nesta fase: retornam `false` de forma conservadora e documentada, nunca lancam excecao nem adivinham um valor.
* **Modifiers** seguem a regra de stacking real do PF2e: bonus/penalidades `untyped` sempre se acumulam; bonus/penalidades de um mesmo tipo nomeado (`circumstance`, `status`, `item`) nao se acumulam entre si — vale o melhor bonus e a pior penalidade de cada tipo; tipos diferentes se acumulam entre si.
* Modifiers com valor dinamico (`brackets`, resolvido por nivel de item/personagem) tambem nao sao resolvidos aqui — este submodulo so opera sobre `value: number` ja resolvido; a resolucao de brackets fica para quando houver contexto de personagem/item real (fase futura).
* **`FlatModifier`**: converte Rule Elements brutos `{key:'FlatModifier', selector, type, value, predicate?}` em `Modifier[]` do substrato, testando o `predicate` contra o roll-options recebido. `selector` pode ser uma string ou uma lista de strings (formato real do compendio) — cada selector gera um `Modifier` proprio. `value` como formula (`"ternary(gte(@item.level,8),3,...)"`) ou `selector` como expressao dinamica (`"{item|flags...}"`) sao reportados em `skipped` com o motivo, nunca avaliados ou adivinhados.
* **`GrantItem`**: decide se um grant de item/effect deve disparar (testando `predicate`) e expoe a referencia bruta (`uuid`) do que deve ser concedido — **nao** resolve o UUID em um documento concreto, isso ja acontece no import do catalogo de magias (Fase 1, `dependencyIds`/`PATHFINDER_2E_SPELL_EFFECT_DEPENDENCIES`). Reproduz fielmente a interacao real de flags do Foundry (auditada no codigo-fonte vendorizado em `pf2e-master/src/module/rules/rule-element/grant-item/`): `inMemoryOnly` forca `reevaluateOnUpdate` e `allowDuplicate` para `true`; caso contrario, `reevaluateOnUpdate` forca `allowDuplicate` para `false`. UUID dinamico (`"{item|flags...}"`) e reportado em `skipped`, nunca resolvido.
* **`RollOption`**: decide, a partir de um `domain`+`option`+`predicate` opcional, qual roll option (string sanitizada, mesma sanitizacao do codigo real) deveria ser adicionada ao contexto — fechando o ciclo "uma regra habilita a proxima" com `testPredicate`. So resolve o subconjunto estatico e nao-interativo: `toggleable` (checkbox de UI) e `suboptions` (selecao do jogador) exigem estado persistido no personagem que este substrato nao tem, e sao reportados em `skipped`, nunca resolvidos com um valor padrao que poderia enganar. `domain` e exposto como metadado, nao concatenado na string do roll option (no sistema real ele e um "balde" de agrupamento, nao um prefixo).
* **`Immunity`/`Weakness`/`Resistance`** (arquivo unico `iwr.ts`, espelhando a base compartilhada real): `type` sempre normalizado para array (um `Modifier`/entrada resolvida por tipo), `mode` (`add`/`remove`) e `override` com os defaults reais (`add`, `false`). `Weakness`/`Resistance` exigem `value` numerico positivo (formula ou `<= 0` -> `skipped`); `Immunity` nao tem valor. `Resistance` preserva `doubleVs`/`exceptions` como listas de strings (entradas de excecao customizada com `definition` sao filtradas, fora de escopo).
* **`TempHP`**: resolve um valor numerico positivo de pontos de vida temporarios; a maioria dos exemplos reais usa formula (`"@item.level"`) e e reportada em `skipped`.
* **`Sense`**: resolve `selector`+`acuity`+`range`, com os defaults reais auditados no codigo-fonte (`range` = `Infinity`/ilimitado quando omitido; `acuity` default `'precise'`, simplificacao documentada da tabela real de acuidades obrigatorias por sentido).
* **`ActorTraits`**: resolve as listas `add`/`remove` de traits, gated por predicate. Nao gera automaticamente os roll options `self:trait:<trait>` que o sistema real cria como efeito colateral — isso e integracao entre familias, fora de escopo.
* **`BaseSpeed`**: resolve `selector` (normalizado removendo sufixo `-speed`, igual ao codigo real) + valor numerico; a maioria dos exemplos reais usa formula baseada em `@actor.attributes.speed.total` e e reportada em `skipped`.
* **`Note`**: resolve notas de chat (`selector`, `text`, `title`, `outcome` opcional), gated por predicate. `text`/`title` sao repassados como strings brutas, sem resolver expressoes Foundry embutidas (`"{item|name}"`) — isso e responsabilidade de um renderer com contexto real de item/ator.
* **`ActiveEffectLike`**: o primitivo generico "mude um campo arbitrario da ficha" do PF2e real (`mode`: `multiply`/`add`/`subtract`/`remove`/`downgrade`/`upgrade`/`override`, `path`, `value`). Como o modo de aplicacao depende do valor *atual* no personagem (que este substrato nao tem), o resolver so expoe a mudanca pendente (`mode`+`path`+`value`), nunca calcula o valor final.
* **`AdjustDegreeOfSuccess`**: resolve o mapa `adjustment` (`success`/`failure`/`criticalSuccess`/`criticalFailure`/`all` -> `"one-degree-better"` etc.) para um `selector`, gated por predicate. Um exemplo real do compendio tem o campo grafado errado (`adjusment`); esse caso simplesmente nao bate com o formato e e ignorado, igual ao schema real faria.
* **`RollTwice`**: resolve `keep` (`higher`/`lower`) + `selector`, gated por predicate.
* **`TokenLight`**: repassa a configuracao de luz do token (`bright`/`dim`/`color`/`animation`) sem interpretar — e dado de apresentacao, nao mecanico.
* **`TokenMark`**: resolve o `slug` do marcador visual do token.
* **`DexterityModifierCap`**: resolve o teto do modificador de Destreza aplicado ao CA. O schema real nao tem campo `selector` — e sempre e apenas sobre CA (confirmado no codigo-fonte, corrigindo uma suposicao inicial que seria adicionada por engano).
* **`Striking`/`WeaponPotency`**: resolvem o bonus de runa de forca/potencia para um `selector` de ataque/dano; a maioria dos exemplos reais tem `selector` e/ou `value` dinamicos e cai em `skipped`.
* **`FastHealing`**: resolve cura por rodada (`value` positivo) com `type` (`'fast-healing'`/`'regeneration'`, default real `'fast-healing'`).
* **`CriticalSpecialization`**: liga o efeito de especializacao critica de uma arma quando o predicate bate; nao tem valor proprio, so conta quantas instancias estao ativas.
* **`MartialProficiency`**: resolve rank de proficiencia marcial. Distingue com cuidado dois predicates diferentes que o Rule Element real tem: `definition` (escopo de quais itens a proficiencia cobre — dominio de item, nao avaliado aqui) e `predicate` (gate do proprio ator — o unico avaliado por este resolver).
* **`EphemeralEffect`**: decide se um effect efemero (existe so durante uma rolagem especifica) deveria ser concedido a `origin` ou `target` de um roll, para selectors especificos — mesma logica de nao-resolucao de UUID do `GrantItem`.

## 4. Personas
* **Desenvolvedor:** usa `testPredicate`/`applyStackingRules` como blocos de montagem ao construir, em fases futuras, o calculo de estatisticas derivadas (AC, saves, Spell DC) e a resolucao de conjuracao.

## 5. Casos de Uso
* Testar se um `Predicate` (extraido de um Rule Element real, ja importado pelo catalogo de magias) bate com um conjunto de roll options.
* Somar uma lista de `Modifier` (mesmo selector) respeitando a regra de stacking do PF2e, retornando o total e quais modifiers efetivamente contaram.

## 6. Limites
Pertence ao submodulo:
* tipos e funcoes puras de roll options, predicates e modifiers/stacking.

Nao pertence ao submodulo (fases futuras do plano):
* implementacao das demais familias de Rule Element (`Aura`, `BattleForm`, `ChoiceSet`, `DamageDice`, `DamageAlteration`, `AdjustStrike`, `Strike`, `ItemAlteration`, `AdjustModifier` etc. — ver lista completa auditada em `.ai/game_systems/pathfinder_2e/spells/questhub-spell-interaction-effects-plan.md` secao 9);
* aplicar de fato um `GrantItem` resolvido (criar o item/effect na ficha do personagem, respeitar `allowDuplicate`/`onDeleteActions`) — este submodulo so decide *se* e *o que* seria concedido, nao executa a concessao;
* toggles e suboptions de `RollOption` (checkbox/selecao na interface do jogador) — exigem estado persistido no personagem e UI, ambos fora de escopo;
* persistir/propagar roll options resolvidos de volta para um `RollOptions` real de personagem — este submodulo devolve a lista do que seria adicionado, quem gerencia o ciclo de vida do contexto e uma fase futura;
* resolucao de expressoes dinamicas Foundry (`{item|...}`, brackets por nivel);
* calculo de estatisticas derivadas alem de CA (saves, pericias, Spell DC, velocidades, sentidos, acoes) — CA ja consome `FlatModifier` via `.ai/game_systems/pathfinder_2e/character_effects/`, as demais continuam hand-rolled;
* degree-of-success, damage alterations, immunities/weaknesses/resistances como comportamento executavel;
* persistencia de efeitos ativos, endpoints HTTP e UI de personagem — isso pertence a `.ai/game_systems/pathfinder_2e/character_effects/`, que so *chama* as funcoes puras deste submodulo.

Ver `.ai/game_systems/pathfinder_2e/spells/questhub-spell-interaction-effects-plan.md` secao 21 para o status completo do plano canonico e secao 22 para as proximas etapas propostas (a mais imediata: ligar este substrato a um consumidor real, ex.: `FlatModifier` com `selector: 'ac'` somado ao calculo de CA existente).
